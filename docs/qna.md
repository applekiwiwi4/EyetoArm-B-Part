# 시험하면서 던진 질문과 결과 (B파트 · 카메라 보정 · 좌표 변환)

> 통합 시험(2026-11-22 ~ 11-24) 중에 "이렇게 하면 되나?"를 하나씩 확인한 기록입니다.
> 각 질문마다 **어떻게 확인했는지**와 **결과**를 적었습니다.

---

## 1. 좌표 정확도

**Q1. B가 계산한 좌표가 실제 볼트 위치와 맞을까?**
- 확인: Gazebo가 알고 있는 실제 볼트 위치를 정답으로 두고, 멈춘 벨트에서 두 볼트의 B 중심점과 비교
- 결과: ✅ 중심 오차 **1.5mm 이내**. 규격 판정도 둘 다 정답

**Q2. 벨트가 움직이는 중에도 좌표가 맞나?**
- 확인: 벨트를 0.02m/s로 돌리고, B 좌표로 볼트 이동 속도를 계산해 실제 벨트 속도와 비교
- 결과: ✅ **19.4~20.5mm/s** (실제 20mm/s), 벨트 방향 위치 오차 **약 1mm**. 촬영 시각과 카메라 위치 동기화가 맞다는 뜻

**Q3. 볼트를 둥근 머리에서 육각 머리로 바꾸면 B 값도 다시 맞춰야 하나?**
- 확인: 육각 볼트 치수(전체 길이, 머리 높이)로 높이와 길이 범위를 다시 계산해 넣고 다시 시험
- 결과: ✅ 필요했음. 갱신 후 두 볼트 모두 판정 정답, 중심 오차 1.5mm 이내 (PR #158)

## 2. 규격 판정

**Q4. 비스듬하게 놓인 작은 볼트를 B가 "판정 불가"로 버리는데, 각도 때문에 길이가 짧게 잡혀서일까?**
- 확인: 같은 자리에 볼트를 두고 각도만 0~150°로 바꾸는 시험 스크립트를 만들어 잰 길이를 기록

| 각도 | 잰 길이 (실제 22mm) | 판정 |
|---|---|---|
| 0° | 19.3mm | 작은 볼트 |
| 45° | 17.8mm | 작은 볼트 |
| 150° | 16.4mm | 판정 불가 (하한 17mm 아래) |

- 결과: ✅ 맞았음. 작은 볼트 길이 하한을 **17 → 14mm**로 낮춰 해결 (PR #172). 큰 볼트 하한이 36mm라 두 규격이 겹치지 않음

**Q5. 60~120°에서 볼트를 못 잡는 것도 B 문제일까?**
- 확인: 같은 각도 시험에서 A 검출 결과부터 확인
- 결과: ❌ B 문제 아님. 그 각도에서는 A(YOLO)가 볼트를 아예 못 찾아서 B까지 값이 오지 않음 → A 파트에 전달

## 3. 집기 높이와 그리퍼

**Q6. 그리퍼가 볼트를 물고 떨다가 시간 초과가 나는데, 그리퍼 설정 문제 아닐까?**
- 확인: 처음에는 설정 문제로 단정했다가, 조건을 하나씩 바꿔 비교 시험. 예전 데모 파일을 물리 엔진만 바꿔서 실행
- 결과: ❌ 설정 문제 아님. Bullet 엔진에서만 실패하고 DART에서는 성공 → C가 DART로 변경
- 배운 점: 원인을 단정하기 전에 비교 시험부터

**Q7. 작은 볼트를 헛잡는데, 손끝 길이 계산이 틀린 걸까?**
- 확인: 손끝 길이 0.0543m로 계산하면 손끝이 지름 3mm 축의 어디에서 멈추는지 계산
- 결과: ✅ 맞았음. 축 한가운데에서 멈춰 제대로 못 감쌌음. **0.0533m**로 고쳐 두 볼트 모두 상자까지 성공

**Q8. 작은 볼트가 미끄러지는데, 2mm 더 낮게 잡으면 되나?**
- 확인: C 데모는 작은 볼트만 2mm 낮게 잡아 성공하고 있었음 → B 목표 높이에 −2mm를 넣고 시험
- 결과: ✅ 벨트를 멈춘 상태에서는 두 볼트 모두 성공

**Q9. 그런데 자동 분류에서는 작은 볼트만 실패하는데, 보정이 두 번 들어간 거 아닐까?**
- 확인: C 자동 분류 코드를 보니 이미 −2mm를 더하고 있었음 → B와 합쳐 **−4mm**, 손끝이 벨트 면 아래로 내려감
- 결과: ✅ 맞았음. B에서 빼고 C 한 곳에만 두어 해결 (PR #167). 자동 분류에서 두 볼트 모두 상자 성공
- 배운 점: 같은 보정이 두 파트에 있으면 실행 경로에 따라 겹친다. 보정은 한 곳에만

**Q10. 작은 볼트가 그리퍼에 박혀서 안 떨어지는데, 그리퍼를 덜 닫으면 안 박히지 않을까?**
- 확인: 작은 볼트일 때만 닫는 정도를 바꿔 시험

| 닫는 정도 | 결과 |
|---|---|
| 0.80 (기존) | 손가락 속으로 파고들어 박힘 |
| 0.70 | 헐거워서 달그락거림 |
| 0.75 | 잘 잡힘 |

- 결과: ✅ 내 PC에서는 0.75로 해결. C 담당 파일이라 바로 합치지 않고 확인용 PR로 올림 (PR #176)

## 4. 연속 분류와 성능

**Q11. 하나 잡고 나면 로봇이 왔다 갔다만 하는데, 부품이 너무 많아서 그런가?**
- 확인: C 서버 기록에서 실패 이유를 집계
- 결과: △ 6번 중 5번이 `TRACK_LOST`. 로봇팔이 볼트를 가려 추적이 끊긴 게 주원인. 부품 수 영향은 공급 간격을 늘려 비교할 예정

**Q12. B 계산 시간 제한을 20ms에서 100ms로 늘리면 버려지는 명령이 줄어들까?**
- 확인: 같은 조건에서 제한값만 바꿔 B_TIMEOUT 횟수 비교
- 결과: ✅ **86번 → 1번**. 다만 A 파트 테스트가 20ms를 고정하고 있어서 A와 합의한 뒤 반영하기로 함

**Q13. 제한을 100ms로 바꿔서 하나도 못 잡게 된 건 아닐까?**
- 확인: 20ms로 되돌리고 다시 실행
- 결과: ❌ 되돌려도 증상이 같음 → 제한값은 원인이 아님

**Q14. B 중심점 영상이 병목이라는 피드백이 왔는데, 실제로 그럴까?**
- 확인: 코드 확인 결과, 사진마다 B 계산 → 영상 그리기 → 발행을 같은 흐름에서 순서대로 처리하고 있음. 그리기와 발행은 20ms 측정에도 포함되지 않음
- 결과: △ 구조상 A 처리 속도를 늦출 수 있음. 단계별 시간을 측정한 뒤 그리기와 발행을 별도 스레드로 분리할 예정

## 5. 실행 환경

**Q15. 시뮬레이션 시간이 뒤로 가고 카메라 FPS가 2배로 나오는데, 왜 그럴까?**
- 확인: `ps`로 실행 중인 프로세스를 확인
- 결과: ✅ 전에 켠 Gazebo가 꺼지지 않고 남아서 두 개가 겹쳐 있었음 → 종료해서 해결. 이후 A가 실행 시 남은 Gazebo를 자동 정리하는 옵션을 추가

**Q16. 팀원은 ROS 도메인 30, 나는 42를 쓰는데 문제가 되나?**
- 확인: 창마다 도메인 번호를 확인
- 결과: △ PC끼리는 달라도 됨. 하지만 내 PC 안의 창들이 30과 42로 섞여 있으면 서로 못 찾아 멈춤 → 모든 창을 42로 통일
